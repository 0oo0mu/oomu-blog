> 이 시리즈는 "선박 부품 품질검사 웹 플랫폼"을 처음부터 끝까지 만드는 전체 과정을 기록한 것입니다. 코드를 한 줄도 모르는 사람도 따라할 수 있도록, 각 단계에서 **왜 이렇게 만들었는지**, **코드가 한 줄 한 줄 무엇을 하는지**, 그리고 **AI의 기본 개념**까지 함께 설명합니다.

## 1. 우리가 만들 것은 무엇인가

조선소에서는 배를 만들 때 여러 단계(용접, 도장, 조립 등)를 거칩니다. 각 단계가 끝나면 사람이 눈으로 부품을 검사해서 "이거 불량이네, 다시 작업해" 또는 "정상이네, 통과"라고 판정합니다.

이 작업을 **AI가 사진을 보고 자동으로 판정**하도록 돕는 웹사이트를 만드는 것이 이 프로젝트의 목표입니다. 구체적으로는:

1. 검사원이 로그인한다
2. 선박과, 그 선박을 구성하는 블록(부품 단위)을 등록한다
3. 블록 사진을 찍어서 업로드하면, **AI가 사진을 분석**해서 정상/불량을 판정한다
4. 불량이면 어떤 종류의 불량인지, 사진의 어느 위치에 있는지, 얼마나 심각한지까지 알려준다
5. 모든 검사 기록은 이력으로 남고, 통계로도 볼 수 있다

### 왜 이런 프로젝트가 의미 있는가

사람이 육안으로 검사하면 다음과 같은 문제가 있습니다.

- **피로에 따른 오차**: 하루 종일 같은 부품을 보다 보면 놓치는 게 생긴다
- **개인차**: 검사하는 사람마다 기준이 조금씩 다르다
- **기록 부재**: "이 부품이 언제, 누가, 무슨 기준으로 검사했는지"가 종이에만 남거나 아예 안 남는 경우가 많다

AI 검사 시스템은 이 세 가지를 어느 정도 보완해줍니다. 다만 AI가 100% 정확한 건 아니라서, **AI는 1차 판정을 돕는 보조 도구**로 쓰고 최종 책임은 사람이 진다는 전제가 깔려 있습니다 (이건 실제 산업 현장의 AI 적용 방식과도 일치합니다).

## 2. 전체 시스템 구조 한눈에 보기

이 시스템은 크게 **3개의 독립된 서버**가 서로 통신하는 구조입니다.

```
┌─────────────────┐       ┌──────────────────┐       ┌─────────────────┐
│   프론트엔드      │       │    AI 서버        │       │    데이터베이스    │
│   (Next.js)      │──────▶│   (FastAPI)       │       │   (Supabase)     │
│  Vercel에 배포    │       │   Render에 배포    │       │                  │
│                  │◀──────┼───────────────────┤◀──────┤  PostgreSQL +    │
│  사용자가 보는 화면 │       │  사진을 받아서      │──────▶│  Auth + Storage  │
└─────────────────┘       │  AI로 분석 후 결과   │       └─────────────────┘
                          │  반환               │
                          └──────────────────┘
```

### 왜 서버를 3개로 나눴는가?

처음 만드는 사람은 "그냥 다 한 군데서 처리하면 안 되나?"라고 생각할 수 있습니다. 나누는 이유는 다음과 같습니다.

| 서버 | 잘하는 일 | 이유 |
|------|----------|------|
| **Next.js (프론트엔드)** | 화면을 그리고 사용자 입력을 받음 | React 기반이라 화면 만들기가 편함 |
| **FastAPI (AI 서버)** | 이미지를 받아 AI 모델로 추론 | AI 모델(PyTorch, ONNX 등)은 Python 생태계가 압도적으로 풍부함. Node.js로는 이런 AI 라이브러리를 쓰기 불편함 |
| **Supabase (DB)** | 데이터 저장, 로그인 인증, 이미지 파일 저장 | 직접 DB 서버를 운영하려면 백업/보안/확장을 전부 신경 써야 하는데, Supabase가 이걸 관리형 서비스로 대신 해줌 |

즉, **"화면은 JS로, AI는 Python으로, 데이터 저장은 전문 서비스에 맡긴다"**는 분업 원칙입니다. 실무에서도 이렇게 역할별로 서버/서비스를 나누는 것을 **마이크로서비스(microservice)** 또는 적어도 **관심사의 분리(separation of concerns)**라고 부릅니다.

## 3. 사용한 기술 스택 정리

| 영역 | 기술 | 한 줄 설명 |
|------|------|-----------|

| AI 서버 | **FastAPI (Python)** | Python으로 API 서버를 빠르게 만들 수 있는 프레임워크 |

| AI 모델 배포 형식 | **ONNX + onnxruntime** | 학습된 모델을 가볍게 추론만 할 수 있는 형식으로 변환 |
| 프론트엔드 배포 | **Vercel** | Next.js를 만든 회사의 무료 배포 서비스 |
| 백엔드 배포 | **Render** | Python 서버를 무료로 배포할 수 있는 서비스 |
| 차트 | **recharts** | React에서 그래프를 그리는 라이브러리 |

## 4. 데이터베이스 구조 미리보기

전체 시스템에서 가장 중요한 것은 **데이터가 어떤 모양으로 저장되는가**입니다. 코드보다 먼저 이걸 이해하면 이후 모든 코드가 훨씬 쉽게 읽힙니다.

```
users (사용자)
  └─ id, email, name, role

ships (선박)
  └─ id, name, ship_type, build_number, status

blocks (블록 = 선박을 구성하는 부품 단위)
  └─ id, ship_id(FK), block_name, process_type, location_description

inspections (검사 결과)
  └─ id, ship_id(FK), block_id(FK), user_id(FK), image_url,
     result(정상/불량), defect_type, confidence,
     inspection_category(용접/표면/조립), severity, recommended_action,
     status(재작업 상태), memo, created_at

defect_logs (불량 위치 박스 - 한 검사에 여러 개 가능)
  └─ id, inspection_id(FK), bbox_x, bbox_y, bbox_width, bbox_height, label, confidence
```

**FK**는 Foreign Key(외래키)의 줄임말로, "다른 테이블의 id를 참조한다"는 뜻입니다. 예를 들어 `blocks.ship_id`는 `ships.id`를 가리킵니다 — "이 블록은 어느 선박에 속해있는가"를 나타내는 연결선입니다.

이 구조를 그림으로 그리면:

```
ships 1 ──── N blocks 1 ──── N inspections 1 ──── N defect_logs
 (선박)        (블록)            (검사 결과)           (불량 위치들)
```

"1 ──── N"은 "하나의 선박에 여러 개의 블록이 속할 수 있다"는 관계(일대다 관계)를 의미합니다.

## 5. 검사 한 건이 만들어지는 전체 흐름

실제로 사용자가 검사를 한 건 수행할 때 시스템 내부에서 무슨 일이 일어나는지 순서대로 따라가 보겠습니다. 이 흐름을 미리 이해하면 이후 모든 블로그 글에서 "이 코드가 왜 필요한지"가 명확해집니다.

1. 사용자가 검사 요청 화면에서 선박/블록을 선택하고 사진을 업로드
2. 프론트엔드가 사진 파일을 **FastAPI AI 서버**로 전송 (`POST /inspect`)
3. AI 서버가 사진을 받아서:
   - ① 카테고리 분류 모델로 "이 사진이 용접/표면/조립 중 무엇인지" 판별
   - ② 판별된 카테고리에 맞는 전용 모델로 불량 여부와 위치를 탐지
   - ③ 결과(정상/불량, 신뢰도, 불량유형, 위치, 심각도, 권장조치)를 JSON으로 응답
4. 프론트엔드가 응답을 받으면:
   - 사진 원본을 **Supabase Storage**(파일 저장소)에 업로드
   - 검사 결과를 **Supabase의 inspections 테이블**에 저장
   - 불량 위치 정보를 **defect_logs 테이블**에 저장
5. 사용자에게 결과 화면을 보여줌 (정상/불량 배지, 사진 위에 빨간 박스로 불량 위치 표시 등)

```
[사용자] → 사진 업로드
    │
    ▼
[Next.js 프론트엔드] → FormData로 AI 서버에 전송
    │
    ▼
[FastAPI AI 서버] → 카테고리 판별 → 불량 탐지 → JSON 응답
    │
    ▼
[Next.js 프론트엔드] → 1) Supabase Storage에 사진 업로드
                      → 2) Supabase DB에 결과 저장
    │
    ▼
[사용자] ← 결과 화면 표시
```

```
│   ├── components/             ← 재사용하는 화면 조각들
│   ├── lib/                    ← 공통 함수/타입 (Supabase 클라이언트 등)
│   ├── middleware.ts            ← 로그인 여부 확인하는 관문 코드
│   └── public/samples/          ← 테스트용 샘플 이미지 모음
│
├── backend/                    ← FastAPI 프로젝트
│   ├── main.py                  ← 서버 진입점
│   ├── routers/inspection.py    ← /inspect API 라우터
│   ├── models/
│   │   ├── dummy_model.py       ← 더미(랜덤) AI 모델
│   │   ├── real_model.py        ← 실제 학습된 AI 모델
│   │   └── weights/             ← 학습된 모델 파일(.onnx)들
│   ├── schemas/inspection.py    ← 요청/응답 데이터 형식 정의
│   └── utils/image.py           ← 이미지 처리 도우미 함수
│
└── venv/                        ← Python 가상환경 (패키지 격리 공간)
```
