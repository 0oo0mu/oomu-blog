## 왜 직접 만들었나?

블로그를 시작하려고 여러 플랫폼을 찾아봤습니다. Tistory, Velog, Notion… 다 좋은데 뭔가 내 마음대로 꾸미기가 어렵더라고요. 그래서 그냥 직접 만들기로 했습니다.

목표는 딱 세 가지였습니다.

- **복잡한 프레임워크 없이** — React나 Next.js 없이 순수 HTML/CSS/JS만으로
- **마크다운으로 글쓰기** — `.md` 파일로 글을 쓰면 자동으로 변환
- **나중에 기능 추가가 쉬운 구조** — 검색, 뮤직 플레이어 등을 쉽게 붙일 수 있도록

---

## 기술 스택

| 구분 | 사용 기술 |
|---|---|
| 마크다운 파싱 | marked.js (CDN) |
| 빌드 도구 | Node.js (build.js) |
| 로컬 서버 | Node.js http 모듈 (server.js) |
| 배포 | GitHub Pages / Netlify / Vercel |
| 기타 | 외부 라이브러리 없음 |

가장 핵심적인 선택은 **프레임워크를 쓰지 않은 것**입니다. 번들러도, 패키지 매니저도 없습니다. `node build.js` 한 번으로 끝납니다.

## 핵심 설계: 이벤트 버스 (app.js)

가장 중요한 설계 결정은 **모듈 간 직접 의존성을 없애는 것**이었습니다.

예를 들어, 검색어가 바뀌면 카드 목록이 업데이트돼야 합니다. 이걸 직접 연결하면 이렇게 됩니다:

```javascript
// ❌ 나쁜 방법: 모듈이 서로를 직접 참조
search.onChange = (query) => {
  filter.setQuery(query);
  renderer.render(filter.getResults());
};
```

이렇게 하면 나중에 기능을 추가하거나 뺄 때 여러 파일을 동시에 고쳐야 합니다.

대신 **이벤트 버스**를 썼습니다:

```javascript
// ✅ 좋은 방법: 이벤트로 소통
// search.js
App.emit('filter:search', { query });

// filter.js
App.on('filter:search', ({ query }) => {
  this.state.query = query;
  this._applyFilter();
});

// renderer.js
App.on('posts:filtered', ({ posts, query }) => {
  this.render(posts, query);
});
```

이 구조의 장점은, 새 기능을 추가할 때 **기존 파일을 건드리지 않아도 된다**는 겁니다. 예를 들어 통계 기능을 추가하고 싶다면:

```javascript
// stats.js 파일만 새로 만들면 됨
App.on('posts:filtered', ({ posts }) => {
  console.log(`현재 ${posts.length}개 포스트 표시 중`);
});
```

## 마크다운 → 블로그 글 변환 과정

글이 화면에 나오기까지의 과정입니다.

### 1. 빌드 단계 (node build.js)

```
posts/PC/언어/C언어기초.md
         ↓
front matter 파싱 (제목, 날짜, 태그)
         ↓
카테고리 = 폴더 경로 ("PC/언어")
         ↓
posts/posts.json 에 메타데이터 기록
```

### 2. 페이지 로드 단계

```
브라우저가 index.html 열기
         ↓
posts.json fetch → 포스트 목록 로드
         ↓
카테고리 트리 + 태그 칩 생성
         ↓
포스트 카드 렌더링
```

### 3. 글 읽기 단계

```
카드 클릭 → post.html?file=PC/언어/C언어기초.md
         ↓
.md 파일 fetch
         ↓
front matter 분리 → 헤더 렌더링
         ↓
marked.js로 마크다운 → HTML 변환
         ↓
h2/h3/h4 태그 스캔 → ToC 자동 생성
```

## ToC (목차) 구현

ToC의 핵심은 **현재 읽고 있는 섹션을 정확히 하이라이트**하는 것입니다.

처음에는 `IntersectionObserver`를 썼는데, heading이 화면 위로 사라지면 하이라이트가 꺼지는 문제가 있었습니다. 섹션이 길면 heading은 이미 위로 올라가고 없는데, 그 섹션 안에 있는 건 맞으니까요.

그래서 **스크롤 위치 기반**으로 바꿨습니다:

```javascript
// 헤더 아래 기준선을 이미 지나친 heading 중 가장 마지막 것 = 현재 섹션
function updateActive() {
  const threshold = window.scrollY + headerHeight + 16;
  let activeId = null;

  for (const heading of headings) {
    if (heading.offsetTop <= threshold) {
      activeId = heading.id; // 계속 갱신 → 마지막 값이 현재 섹션
    } else {
      break; // 더 아래 heading은 볼 필요 없음
    }
  }

  setActive(activeId);
}
```

이 방식은 섹션이 아무리 길어도 항상 정확하게 하이라이트됩니다.

## 계층형 카테고리 사이드바

글을 `posts/PC/언어/C/hello.md`에 넣으면 카테고리가 자동으로 `PC/언어/C`가 됩니다. build.js가 폴더 경로를 읽어서 처리하기 때문입니다.

사이드바의 트리는 이 경로들을 파싱해서 만듭니다:

```javascript
// "PC/언어/C" → 트리 노드 생성
const parts = "PC/언어/C".split('/'); // ['PC', '언어', 'C']
let node = root;
parts.forEach(part => {
  if (!node._children[part]) {
    node._children[part] = { _posts: 0, _children: {} };
  }
  node = node._children[part];
});
```

"PC"를 클릭하면 `PC/언어`, `PC/언어/C`, `PC/언어/JAVA` 등 하위 카테고리의 글도 모두 표시됩니다:

```javascript
// 상위 폴더 클릭 시 하위 글도 포함
const catOk = post.category === category
           || post.category.startsWith(category + '/');
```

## 배포

빌드 결과물이 모두 정적 파일(HTML, CSS, JS, JSON)이라서 어디든 올릴 수 있습니다.

### GitHub Pages

1. GitHub 저장소에 push
2. Settings → Pages → Source: GitHub Actions
3. 이후 push할 때마다 자동 배포 (`.github/workflows/deploy.yml`)

### Netlify / Vercel

저장소를 연결하면 끝입니다. `netlify.toml` / `vercel.json`에 빌드 명령어가 설정되어 있어서 자동으로 `node build.js`를 실행하고 배포합니다.

## 글 쓰는 방법

1. `posts/카테고리/파일명.md` 생성
2. 맨 위에 front matter 작성:

```markdown
---
title: 글 제목
date: 2026-06-02
tags: [태그1, 태그2]
---

## 본문 시작

여기부터 마크다운으로 씁니다.
```

3. `node build.js` 실행
4. 브라우저 새로고침

에디터(`editor.html`)를 쓰면 마크다운을 실시간으로 미리보면서 작성하고, 저장 버튼으로 바로 파일을 저장할 수 있습니다.

## 마무리

처음에는 "그냥 HTML 몇 개 만들면 되겠지"라고 생각했는데, 생각보다 고민할 게 많았습니다. 특히 모듈 간 의존성을 어떻게 끊을지, ToC 하이라이트를 어떻게 정확하게 할지가 가장 어려웠어요.

결과적으로 꽤 만족스러운 구조가 나왔습니다. 새 기능을 추가할 때 파일 하나만 만들고 `app-index.js`에 두 줄만 추가하면 되니까요.

앞으로 댓글 기능, 방문자 통계, 다국어 지원 같은 것도 추가해보고 싶습니다.
