# 코드 구조와 이벤트 버스

지금까지는 파일 하나(`app.js`)에 코드를 몰아 넣었습니다. 하지만 앞으로 목록·사이드바·검색·다크모드·그래프… 기능이 계속 늘어납니다. 아무 계획 없이 쌓으면 금세 **스파게티 코드**(서로 얽혀 손대기 무서운 코드)가 돼요. 이번 편에서 기능들을 깔끔하게 조립할 **뼈대**를 먼저 잡습니다. 이 블로그의 심장인 **`app.js`(이벤트 버스)**를 만듭니다.

## 문제: 모듈이 서로 직접 부르면 생기는 일

블로그를 여러 조각(모듈)으로 나눈다고 해봅시다.

- `posts-loader` — 글 목록을 불러옴
- `renderer` — 목록을 카드로 그림
- `sidebar` — 카테고리 트리를 그림
- `filter` — 카테고리/검색으로 걸러냄

만약 `posts-loader`가 글을 다 불러온 뒤에 `renderer`, `sidebar`, `filter`를 **직접 하나하나 호출**한다면 어떻게 될까요?

```javascript
// 나쁜 예시
loadPosts();
renderer.render(posts);
sidebar.build(posts);
filter.setPosts(posts);
// 나중에 graph도 추가되면 여기에 또 한 줄...
```

기능을 추가/삭제할 때마다 `posts-loader`를 **계속 열어 고쳐야** 합니다. 모듈들이 서로를 너무 잘 알고 꽉 얽혀 있죠(=결합도가 높다). 이러면 하나 바꿀 때 다른 게 줄줄이 깨집니다.

## 해결: 이벤트로 소통하기 (이벤트 버스)

대신 이렇게 합니다.

- `posts-loader`는 글을 다 불러오면 그냥 **"글 다 불러왔어!"** 하고 **방송(emit)**만 합니다. 누가 듣든 신경 안 씁니다.
- `renderer`, `sidebar`, `filter`는 각자 **"글 다 불러왔다는 방송이 나오면 나 이거 할래"** 하고 **구독(on)**해 둡니다.

이 "방송국" 역할을 하는 중앙 장치가 **이벤트 버스**입니다. 비유하면 **라디오 방송**이에요. 방송하는 쪽은 청취자가 누군지 몰라도 되고, 청취자는 자기가 관심 있는 채널만 들으면 됩니다. 서로 직접 아는 사이가 아니라서(=결합도가 낮아서), 기능을 추가·제거해도 다른 파일을 안 건드립니다.

세 가지 동작만 있으면 됩니다.

- **register(등록)** — 모듈을 앱에 등록하고 자동으로 켜기(init)
- **emit(발행)** — 이벤트를 방송하기
- **on(구독)** — 이벤트를 듣기

## 실제 파일 — js/core/app.js

`js` 폴더 안에 `core` 폴더를 만들고(핵심 부품용), 그 안에 `app.js`를 만드세요. (`js/core/app.js`) 이 블로그 실제 코드 그대로입니다.

```javascript
/**
 * js/core/app.js — 앱 중앙 레지스트리 & 이벤트 버스
 *
 * 모든 모듈은 App을 통해 서로 소통합니다.
 * 직접 import 대신 이벤트를 쓰면 결합도가 낮아져,
 * 기능을 추가/제거해도 다른 파일을 안 건드려도 됩니다.
 */

const App = {
  /** 등록된 모듈들 { 이름: 모듈객체 } */
  modules: {},

  /** 이벤트 리스너들 { 이벤트명: [콜백, ...] } */
  _listeners: {},

  /**
   * 모듈을 등록하고, init()이 있으면 자동 호출합니다.
   */
  register(name, module) {
    this.modules[name] = module;
    if (typeof module.init === 'function') {
      module.init();
    }
  },

  /**
   * 이벤트를 발행합니다. 구독한 모든 콜백이 즉시 실행됩니다.
   */
  emit(event, data) {
    const listeners = this._listeners[event] || [];
    listeners.forEach(cb => {
      try {
        cb(data);
      } catch (e) {
        console.error(`[App] 이벤트 핸들러 오류 (${event}):`, e);
      }
    });
  },

  /**
   * 이벤트를 구독합니다.
   * @returns {Function} 구독 해제 함수
   */
  on(event, cb) {
    if (!this._listeners[event]) {
      this._listeners[event] = [];
    }
    this._listeners[event].push(cb);

    // 구독 해제 함수 반환
    return () => {
      this._listeners[event] = this._listeners[event].filter(fn => fn !== cb);
    };
  },

  /**
   * 등록된 모듈을 이름으로 가져옵니다.
   */
  get(name) {
    return this.modules[name];
  },
};

export default App;
```

## 한 부분씩 해설

### 데이터 두 개

- **`modules: {}`** — 등록된 모듈들을 이름표와 함께 담아두는 보관함. `{ sidebar: ..., search: ... }` 형태가 됩니다.
- **`_listeners: {}`** — 이벤트별 구독자(콜백) 목록. `{ 'posts:loaded': [함수1, 함수2] }` 형태예요. 이름 앞의 `_`는 "이건 내부용, 밖에서 직접 만지지 마"라는 관습적 표시입니다.

### register(name, module)

```javascript
register(name, module) {
  this.modules[name] = module;
  if (typeof module.init === 'function') {
    module.init();
  }
}
```

모듈을 보관함에 넣고, 그 모듈에 `init`이라는 함수가 있으면 **자동으로 실행**합니다. 그래서 우리는 나중에 `App.register('search', Search)` 한 줄이면 검색 모듈이 등록되고 스스로 초기화까지 됩니다. `this`는 "이 App 객체 자신"을 가리켜요. `typeof ... === 'function'`은 "그게 진짜 함수인지" 확인하는 방어 코드입니다(없어도 에러 안 나게).

### emit(event, data)

```javascript
emit(event, data) {
  const listeners = this._listeners[event] || [];
  listeners.forEach(cb => {
    try { cb(data); }
    catch (e) { console.error(...); }
  });
}
```

특정 이벤트를 방송합니다. 그 이벤트를 구독한 콜백(`cb`)들을 하나씩 꺼내 `cb(data)`로 실행하며 데이터를 넘깁니다. `|| []`는 "구독자가 아무도 없으면 빈 목록으로 취급"이라 에러가 안 납니다. `try { } catch { }`는 **한 구독자가 에러를 내도 나머지는 계속 실행**되게 감싸주는 안전장치예요(에러는 콘솔에만 찍음).

### on(event, cb)

```javascript
on(event, cb) {
  if (!this._listeners[event]) this._listeners[event] = [];
  this._listeners[event].push(cb);
  return () => { ... };  // 구독 해제 함수
}
```

특정 이벤트에 콜백을 등록(구독)합니다. 그 이벤트의 목록이 아직 없으면 빈 배열부터 만들고, 거기에 콜백을 `push`(추가)합니다. 그리고 **구독을 취소하는 함수**를 돌려줍니다. 나중에 "이 구독 그만 들을래" 할 때 그 함수를 부르면 목록에서 자기 콜백만 `filter`로 빼냅니다. (지금은 안 써도, 나중에 목차처럼 페이지를 새로 그릴 때 옛 구독을 정리하는 데 쓰입니다.)

### get(name)

등록된 모듈이 정말 필요할 때 이름으로 꺼내 쓰는 통로입니다. 대부분은 이벤트로 소통하지만, 가끔 직접 참조가 필요할 때 대비한 겁니다.

## 이 패턴이 앞으로 어떻게 쓰이나 (미리 감 잡기)

앞으로 진입점 파일(예: `app-index.js`)에서 이렇게 조립하게 됩니다.

```javascript
import App         from './core/app.js';
import PostsLoader from './modules/posts-loader.js';
import Renderer    from './modules/renderer.js';

// 1) 렌더러가 "글 걸러졌다" 방송을 구독
App.register('renderer', Renderer);   // Renderer.init() 안에서 App.on(...) 구독

// 2) 로더가 글을 불러오고 "posts:loaded" 방송
PostsLoader.load();                   // 끝나면 App.emit('posts:loaded', ...)
```

로더는 렌더러의 존재를 몰라도 되고, 렌더러는 로더가 언제 부르든 방송만 오면 그립니다. **각자 자기 일만** 하죠. 새 기능(그래프 등)을 붙일 때도 그 모듈에서 필요한 방송만 구독하면 되고, 기존 파일은 안 건드립니다. 이게 이 블로그가 기능을 20개 가까이 얹고도 안 무너지는 이유예요.

## 자주 나는 실수

- **`App.on(...)`을 `App.emit(...)`보다 늦게 등록** → 방송이 먼저 나가버려 아무도 못 듣습니다. **구독(on/register)을 먼저, 발행(emit/load)을 나중에.** (뒤에서 라우터를 붙일 때 이 순서 때문에 실제로 버그가 났던 부분이라 특히 조심.)
- **이벤트 이름 오타** → `'posts:loaded'`를 한쪽은 `'post:loaded'`로 쓰면 조용히 아무 일도 안 일어납니다. 이름을 상수처럼 정확히.
- **`export default App` 빠뜨림** → 다른 파일에서 `import`가 안 됩니다.

## 정리

- 기능이 많아지면 모듈이 서로 직접 부르는 방식은 금방 얽힌다.
- **이벤트 버스**(app.js)로 모듈들이 **방송(emit)/구독(on)**으로 느슨하게 소통하게 한다.
- `register`는 모듈 등록+자동 init, `emit`은 방송, `on`은 구독(+해제 함수 반환), `get`은 직접 참조.
- 규칙: **구독을 먼저, 발행을 나중에.**
